navTitle: game
description: Run a timed game session from a JSON plan, inject inputs, and measure visual changes and capture timing.
---

`game` runs one bounded session against a window and returns a structured report. It does not read the accessibility tree. It observes the window by continuous capture and measures how the picture changes over time, so it works on games and other surfaces that expose no tree.

The command requires Windows 10 version 2004 or newer for cursor-controlled
window capture. On other platforms it fails with `PLATFORM_NOT_SUPPORTED`.
On Windows, a click-through control notice appears for the duration of a session
with input. It follows the Windows display language and falls back to English.
Observation-only sessions do not show it. If the notice cannot be displayed,
the session fails before sending input.

```bash
acdesktop game --app MyGame --plan plan.json --out .\session --headed
```

Plans with input require `--headed` and focus the target. Input stops if the target loses foreground ownership or moves. Observation-only plans do not focus the window.

Mouse events move the visible system cursor. To include the system cursor in
saved PNGs, set `capture_cursor` to `true` in the plan and pass `--save-frames`.
The cursor appears only while the OS displays it over the captured window. A
second capture session supplies these images; the report's visual metrics use
the separate cursor-free session and are not synchronized to each saved frame.

## The plan

A plan is one JSON object. Timing is in milliseconds from the start of the session. Event `x` and `y` are pixels inside the window's client area; the session adds the client origin before injection. A window screenshot can include non-client borders.

```json
{
  "duration_ms": 4000,
  "fps": 30,
  "capture_cursor": false,
  "events": [
    { "at_ms": 200, "action": "key", "key": "W", "hold_ms": 400 },
    { "at_ms": 900, "action": "mouse-move", "x": 640, "y": 360 },
    { "at_ms": 1100, "action": "mouse-click", "x": 640, "y": 360, "button": "left" },
    { "at_ms": 1500, "action": "gesture", "gesture": "tap", "x": 640, "y": 360 },
    { "at_ms": 2000, "action": "gesture", "gesture": "pinch-out", "x": 640, "y": 360, "distance": 200, "duration_ms": 300 },
    { "at_ms": 3000, "action": "touch", "contacts": [{ "id": 0, "x": 300, "y": 400 }], "hold_ms": 120 }
  ],
  "probes": [
    { "name": "jump", "event": 0, "timeout_ms": 2000, "min_change": 0.002 }
  ]
}
```

An event's `action` selects its shape:

| `action` | Fields | Effect |
| --- | --- | --- |
| `key` | `key`, `hold_ms` | Hold a key for `hold_ms`, then release it. |
| `key-down` | `key` | Press and hold a key until the session ends or `key-up` releases it. |
| `key-up` | `key` | Release a key. |
| `mouse-move` | `x`, `y` | Move the cursor. |
| `mouse-down` | `x`, `y`, `button` | Press a pointer button. `button` is `left`, `right`, or `middle`. |
| `mouse-up` | `x`, `y`, `button` | Release a pointer button. |
| `mouse-click` | `x`, `y`, `button` | Press and release at a point. |
| `gesture` | `gesture`, `x`, `y`, `duration_ms`, `distance` | Expand a named gesture into touch frames. |
| `touch` | `contacts`, `hold_ms` | Send one touch frame of contacts, then release them after `hold_ms`. |
| `touch-path` | `frames` | Play explicit, timed frames of simultaneous contacts. |

A contact is `{ "id": 0, "x": 640, "y": 360, "phase": "move" }`. The phase defaults to `move`; set it to `down` or `up` to control a contact frame directly. The session attempts to release held keys, buttons, and contacts when it returns, including on errors. Forced process termination can prevent cleanup.

### Gestures

`gesture` expands into a sequence of touch frames from `(x, y)`. `distance` stretches swipes, pinches, and rotates; `duration_ms` bounds the motion.

`tap`, `double-tap`, `long-press`, `swipe-left`, `swipe-right`, `swipe-up`, `swipe-down`, `pinch-in`, `pinch-out`, `rotate-cw`, `rotate-ccw`, `two-finger-tap`, `draw-s`, `circle-cw`, `circle-ccw`, `three-finger-swipe-left`, `three-finger-swipe-right`, `three-finger-swipe-up`, `three-finger-swipe-down`.

Pinches and rotations use two contacts; three-finger swipes use three. Windows
injects synthetic multi-touch, but the target or the system may consume or
ignore it. Verify touch events or game state independently. A successful
command reports injection, not game recognition.

On Windows 11, system gestures reserve three- and four-finger touch by default.
Before a session with three or more contacts, turn off **Three- and four-finger
touch gestures** in **Settings → Bluetooth & devices → Touch**, then set
`"acknowledge_system_gesture_conflict": true` in the plan. The command cannot
verify that setting. If it is enabled, the gesture can switch windows or
desktops instead of reaching the game. Restore the setting after testing if
you need Windows gestures. See [Microsoft's touch guidance](https://learn.microsoft.com/en-us/troubleshoot/windows/win32/finger3or4-touch-interaction-no-longer-works).

Use `touch-path` to draw an S, drag around a curve, or hold a virtual joystick while another finger taps. Frame `at_ms` values are offsets from the event's `at_ms`, must increase strictly, and must finish before `duration_ms`. Each frame contains every contact still held; mark each contact `up` once at its last position. For example:

```json
{"duration_ms": 1500, "events": [{"at_ms": 100, "action": "touch-path", "frames": [
  {"at_ms": 0, "contacts": [{"id": 0, "x": 100, "y": 300, "phase": "down"}]},
  {"at_ms": 100, "contacts": [{"id": 0, "x": 140, "y": 300, "phase": "move"}, {"id": 1, "x": 500, "y": 300, "phase": "down"}]},
  {"at_ms": 200, "contacts": [{"id": 0, "x": 140, "y": 300, "phase": "move"}, {"id": 1, "x": 500, "y": 300, "phase": "up"}]},
  {"at_ms": 300, "contacts": [{"id": 0, "x": 140, "y": 300, "phase": "up"}]}
]}]}
```

### Probes

A probe measures the time from an input dispatch to the first comparable picture change at or above `min_change`, or until `timeout_ms` passes. The first captured frame is a baseline, not a comparison. An unrelated animation can satisfy the probe, and capture sampling limits its precision.

```json
{ "name": "menu", "event": 2, "timeout_ms": 1500, "min_change": 0.01 }
```

`min_change` is the fraction of sampled pixels that must differ from the previous frame, from `0` to `1`. The default is `0.002`.

## The report

The command returns the report path, the plan path, the window id, and the report itself under `summary`. With `--save-frames` it adds `frames_saved`, the number of frames written to disk; the writer is best-effort, so this can be lower than `frame_metrics.sampled` when the encoder trails the capture rate. It also writes the report object alone to `<out>/report.json`.

Set `brief_response: true` in the plan to reduce response size for many
probes. The response replaces `summary.probes` with `summary.probe_summary`
containing `total` and `responded`; the report file remains complete.

```json
{
  "version": "2.6",
  "ok": true,
  "command": "game",
  "data": {
    "report": "C:\\session\\report.json",
    "plan": "C:\\session\\plan.json",
    "window": "w-2104",
    "frames_saved": 109,
    "summary": {
      "duration_ms": 6999,
      "planned_ms": 7000,
      "truncated": false,
      "width": 1280,
      "height": 720,
      "frames": 211,
      "inputs": 28,
      "cursor_in_saved_frames": false,
      "frame_metrics": {
        "sampled": 119,
        "fps": 29.8,
        "interval_ms": { "min": 31, "median": 33, "max": 41, "stdev": 2.1 },
        "dropped": 1
      },
      "input_metrics": { "dispatched": 6, "jitter_ms": { "min": 0, "median": 1, "max": 4, "stdev": 1.2 } },
      "probes": [
        { "name": "jump", "event": 0, "timeout_ms": 2000, "responded": true, "latency_ms": 66 }

        "active_ratio": 0.72,

```

The `flow` fields describe visual activity, not a player's psychological flow or engagement. A changed frame may come from an animation unrelated to the input. Use game telemetry and player observation to assess experience.

## Reading the result

The report measures the session, so run it twice and compare. A change in `latency_ms` or `interval_ms` between an otherwise identical plan points at the app, the driver, or the machine. A session that never changes is not proof the app is frozen; it may be a window the capture API cannot see, such as a fullscreen exclusive surface. Open the game windowed or borderless, and check `ok` and `probes` before trusting a quiet session.

`--save-frames` writes the sampled frames for offline review. The files are BGRA captured and PNG encoded; the writer thread encodes and writes as the session runs, so a slow disk or encoder drops frames instead of slowing the input timeline. The count is in `frames_saved`.

`frames/frames.jsonl` maps each saved PNG to `at_ms`, measured from the start
of the session. Frames can be skipped when the capture or writer cannot keep
up; use these timestamps rather than assuming a fixed interval.

`--timeout-ms` defaults to `duration_ms` plus 20 seconds, enough for the lease, the window focus, and the cold capture setup. A session that reports `truncated: true` stopped early: usually the command's deadline, so raise `--timeout-ms` above the plan's duration.

If a session ends before every scheduled input step is dispatched, it returns an error instead of a completed report. If an input step fails after earlier steps were dispatched, or the report cannot be written after input, the session's delivery is unknown. Inspect the game state before retrying.

The report is created only if its path is still unused at the end of the session. A concurrent report is never replaced. If writing fails after creation, the directory may contain an incomplete report; use a fresh output directory for another run.
